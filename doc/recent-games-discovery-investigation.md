# recent_games 발굴 방식 조사 기록 (2026-08-14)

`recent_games_pipeline`이 "최근 출시 + 평가 좋은" 게임 후보를 찾는 방법을 여러 번 갈아엎은 기록.
결론부터: **무료 비공식 Steam Store 검색 API로는 "최근 N개월 + 리뷰 M개 이상"을 깔끔하게 못 찾는다.**
현재 코드는 동작은 하지만 느리고(수십 분) 히트율이 낮다(수십 개 중 한두 개). 다음 세션에서 이어서
고민할 것.

---

## 문제 상황

`old_games_pipeline`(SteamSpy `all` 페이지네이션, 옛 명작 발굴)과 별개로, `recent_games_pipeline`은
"최근 나온 괜찮은 게임"을 매주 발굴해야 한다. 후보 조건:

- 출시일이 최근 N개월/1년 이내
- 긍정 리뷰(`positive`)가 어느 정도 있어야 함 (사용자 요청: 100개 미만은 후보에서 제외, 100~999는
  "숨겨진 맛집" 톤으로 소개, 1000 이상은 일반 톤 — `langgraph-server/app/prompts.py` 참고)
- DLC/사운드트랙/데모/소프트웨어 제외 (진짜 게임만)

---

## 시도 1: `released=Custom&from=&to=` 날짜 필터 — 완전히 무시됨

`store.steampowered.com/search/results/`에 `sort_by` + `released=Custom&from=&to=`를 같이 넘기면
공식 웹사이트 검색 UI가 하는 것과 같은 필터링이 될 거라 기대했다. **실측 결과: 어떤 `sort_by` 값을
넣어도(`Released_DESC`, `Released_ASC`, `Reviews_DESC`, `Rating_DESC`, `Top_Sellers_DESC`,
`Trending_DESC` 전부) 날짜 파라미터가 그냥 무시된다.**

증거: "1년 전~2일 전" 구간을 요청해도:
- `sort_by` 없음 / `Rating_DESC` / `Top_Sellers_DESC` / `Trending_DESC` → PUBG, Palworld, Apex Legends,
  Counter-Strike 2 같은 상시 인기작만 나옴 (출시일 무관)
- `Released_DESC` → **요청한 과거 구간과 무관하게 항상 오늘 날짜 게임만 나옴** (appid 4635890,
  3831700, 3816710 등 전부 실제 출시일이 "14 Aug, 2026" = 오늘로 확인됨. 심지어 "coming soon"
  게임까지 섞여 나온 적 있음)
- `Released_ASC` → 역시 PUBG/Palworld 등, 날짜 무시

**교훈: 이 엔드포인트의 `released` 파라미터는 서버 쪽에서 아무 역할도 안 한다고 간주해야 한다.**
"구간을 여러 개로 쪼개서 여러 번 요청"해도 각 요청이 전부 같은(필터 무시된) 결과를 반환하므로
아무 의미가 없다 — 처음에 "1년을 30일 구간으로 슬라이스"하는 방식을 시도했다가 이 사실을 뒤늦게
깨닫고 폐기했다.

---

## 시도 2: `sort_by=Released_DESC` 단독 + 순차 페이지네이션 — 밀도가 너무 낮음

날짜 파라미터 없이 `sort_by=Released_DESC`만 쓰면 **정렬 자체는 정확하다**(카탈로그를 출시일
내림차순으로 순회하는 건 맞음). 그래서 "일단 넓게 긁고, 후보마다 Steam 공식 appdetails로 실제
출시일을 확인해서 우리가 직접 걸러낸다"는 전략으로 전환.

문제: **Steam은 하루에도 저품질 신작(대부분 리뷰 0개)을 수백 건씩 등록한다.** 실측으로 `start=0`부터
순차로 진짜 게임(`type=="game"`) 100개를 연속으로 확인했는데 **전부 오늘(2026-08-14) 출시, 전부
`positive=0`**이었다. 즉 오늘 하루치만 훑어도 100개를 넘는다는 뜻 — 1년 전까지 순차로 내려가려면
수만 번의 API 호출(appid당 1req/s)이 필요해서 사실상 불가능(수 시간~며칠).

---

## 시도 3: `Released_DESC` + 이진 탐색으로 "1년 전" 지점 먼저 찾기 — 작동은 하나 느림, 사용자 거부

검색 결과가 출시일 내림차순으로 정렬된다는 걸 이용해, `start` 오프셋에 대해 이진 탐색으로 "목표
날짜(예: 1년 전)"에 해당하는 지점을 몇십 번의 프로브만으로 찾고, 거기서부터 최신 쪽으로 훑는 방식.

실측: `max_count=20`(1년 창) 기준 이진 탐색 자체는 64초 만에 완료, 이후 수집한 20개 중 3개가
`positive` 768/150/63으로 실제 리뷰 있는 게임이었다(나머지는 여전히 0). `Released_DESC` 순차보다는
훨씬 나음.

**사용자 피드백으로 폐기**: "SteamSpy처럼 인기 랭킹 1~N위 순으로 도는 거 아니냐"는 우려 제기.
설명은 드렸지만(랭킹이 아니라 날짜 정렬), 더 근본적으로 "무조건 날짜 정렬 훑기"보다 "평가 좋은
순으로 가져와서 걸러내자"는 대안을 요청받아 방향 전환.

## 시도 4(현재): `sort_by=Reviews_DESC` + 클라이언트 날짜 필터 — 부분 성공, 히트율 낮음

`Reviews_DESC`("평가 좋은 순", 정확한 정렬 기준은 비공개)로 순차 페이지네이션하면서 후보마다 실제
출시일을 확인해 window 안에 있는 것만 남기는 방식. `Reviews_DESC`는 날짜순이 아니라서 "경계를
넘으면 멈춘다" 최적화는 못 쓰고, `max_count`를 채우거나 안전장치(`STEAM_SEARCH_MAX_PAGES`)에
도달할 때까지 계속 훑어야 한다.

### 실측 데이터

| 창(window) | 시도한 개수 | 소요 시간 | `positive>=100` 통과 | 비고 |
|---|---|---|---|---|
| 1년 (365일) | 20개 | 64초 | 3개 (768/150/63) | 초반 이진탐색 버전과 혼용 테스트 |
| 1개월 (30일) | 30개 목표 | **24분+ 못 채움** (강제 종료) | 0개 확보 | 밀도 너무 낮아 중단 |
| 3개월 (90일) | 30개 | **22분 15초** | 2개 (21452/19544) | 나머지 28개 전부 0 |

**결론**: `Reviews_DESC`도 여전히 검색 결과 대부분(28/30, 27/30 등)이 리뷰 0개인 신작으로 채워진다
— "평가 좋은 순" 정렬이라기보다, 신작이 계속 섞여 들어오는 피드에 가까운 것으로 보인다. 창을
넓혀도(1개월→3개월) 통과율이 크게 개선되지 않았다(1개월은 아예 30개를 못 채울 정도로 더 나쁨 —
갓 나온 게임은 `Reviews_DESC` 상위권에 오를 시간 자체가 없어서로 추정).

### 현재 코드 상태

`develope/spark-jobs/jobs/ingest.py`:
- `RECENT_WINDOW_SPAN_DAYS = 90` (3개월)
- `RECENT_MIN_POSITIVE_REVIEWS = 100`
- `discover_recent_game_appids()`: `sort_by=Reviews_DESC`로 페이지네이션, 후보마다
  `fetch_steam_official_appdetails`로 실제 출시일 확인, window 안 + `type=="game"`인 것만 수집
- `STEAM_SEARCH_MAX_PAGES = 300` (안전장치)
- `main()`에서 `RECENT_MAX_CANDIDATES`(Airflow Variable) 없으면(운영 모드) 무제한으로 훑음 —
  실측 기준 수십 분 이상 걸릴 수 있음

이 자체는 **틀린 코드는 아니다** — 실제로 매번 몇 개씩은 정상적으로 찾아낸다. 다만 느리고
비효율적이다. 주간 배치라 사람이 실시간으로 기다릴 필요는 없다는 점을 감안하면 "일단 쓸 수는
있는" 상태.

## 다음 세션에서 고민할 옵션

1. **지금 방식(3개월 + Reviews_DESC + 100개 필터) 그대로 운영 배치 실행** — 느리지만(주 1회
   수십 분) 정확하게는 동작. 아직 실제 `recent_games_pipeline` 전체 실행으로 검증은 안 함
   (`docker run`으로 로직만 단독 테스트한 상태).
2. **공식 Steam API 키 발급 검토** — `IStoreService/GetAppList`(이미 `fetch_steam_official_app_list`로
   구현은 되어 있으나 미사용, `main()`에 주석 처리됨)나 다른 공식 엔드포인트가 날짜/리뷰 필터를
   서버 사이드에서 제대로 지원하는지 재조사.
3. **SteamDB 등 제3자 데이터 소스 검토** — 크롤링 정책/이용약관 확인 필요.
4. **전략 자체를 재검토**: "최근 3개월 + 리뷰 100개 이상"이라는 조건 자체가 시장에 흔치 않은
   조합일 수 있음(막 나온 게임은 리뷰가 적을 수밖에 없는 게 자연스러운 현상). 임계값(100)이나
   창(3개월)을 사용자 요구사항과 다시 맞춰볼 필요.

## 참고: 이 세션에서 같이 고친 관련 버그(참고용, 위 이슈와 별개)

- `postgres_load.py`의 `load_gold_to_postgres`가 UPDATE 시 `ingested_at`을 덮어써서 "1년 이내"
  신선도 필터가 사실상 무력화되던 버그 → UPDATE 절에서 `ingested_at` 제외로 수정
- `bronze.py`가 raw 데이터가 하나도 없을 때(이번 실행에 필터 통과한 후보가 0개) `PATH_NOT_FOUND`로
  파이프라인 전체가 죽던 버그 → 빈 스키마 DataFrame으로 폴백하도록 수정
- `postgres_load.py`의 `load_gold_to_postgres`가 빈 gold 스냅샷에서 `execute_values`를 빈 리스트로
  호출하던 것 → 빈 리스트면 그냥 스킵하도록 방어 코드 추가
