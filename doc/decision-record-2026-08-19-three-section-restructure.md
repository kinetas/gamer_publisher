# 결정 기록: 신작 발굴 폐기 → RSS/명작 아카이브/감성분석 3섹션 재구성 (2026-08-19)

`/complainProject`로 수집한 변경 요청(`doc/CHANGE_REQUEST.md`)의 배경과, 논의 중 설계가 바뀐 이유를 나중에
트러블슈팅할 때 참고할 수 있도록 별도로 남겨둔다.

---

## 원래 컨셉이었던 것

- **`recent_games_pipeline`**: "최근 N개월 이내 출시 + 긍정 리뷰 100개 이상"인 신작을 Steam 검색 API로
  능동 발굴해서 "새로운 게임" 섹션에 자동 노출. `old_games_pipeline`(SteamSpy `all` 순회, 구작 명작 발굴)과
  대응되는 짝 개념으로 설계됨.
- 상세 시도 기록: `doc/recent-games-discovery-investigation.md` (시도 1~4, 전부 부분 실패 또는 저효율로 종결)

## 왜 원래 컨셉을 버렸나

- Steam 비공식 검색 API(`store.steampowered.com/search/results/`)의 `released` 날짜 파라미터가 서버에서
  완전히 무시됨 → 순차/이진탐색/`Reviews_DESC` 등 여러 우회를 시도했지만, 매일 등록되는 리뷰 0개짜리
  저품질 신작이 결과 대부분을 차지해 실제 후보를 걸러내는 데 수십 분이 걸리고 히트율도 낮았음(수십 개 중 1~2개)
- 이건 "카탈로그 전체에서 미지의 대상을 조건으로 찾아내야 하는" 구조적 문제 — API가 서버 사이드 필터를
  지원하지 않는 이상 근본적으로 해결이 안 됨
- 결론: 이 방식 자체를 폐기하고, "이미 알려진 소식(RSS)을 그대로 보여주는" 방식으로 목적을 바꿈
  (신작을 우리가 능동적으로 찾아내는 대신, 게임 미디어가 이미 골라서 보도한 걸 가져옴)

## 설계가 중간에 바뀐 부분: 감성분석

- **처음 제안**: 리뷰 감성분석을 기존 LLM API(자체 LLM 우선, OpenAI fallback)만으로 처리하려 했음
- **문제 제기**: 리뷰 전량을 LLM에 넣으면 호출량이 많아져 비용/속도 면에서 `recent_games_pipeline`이
  겪었던 병목과 비슷한 문제가 재발할 수 있다는 지적을 받음. 또한 "라이브러리도 같이 써도 된다"는 요구사항이
  처음부터 있었는데 반영이 안 되어 있었음
- **수정된 설계**: 경량 사전학습 다국어 감성분석 라이브러리(로컬, HuggingFace transformers 기반)로 리뷰
  전량을 1차 분류(긍/부정/점수) → 집계 결과 + 대표 샘플만 LLM에 배치로 넣어 요약 리포트 생성(2차 종합).
  LLM 호출량을 리뷰 개수가 아니라 게임 개수 수준으로 줄임

## 감성분석 대상 게임의 appid를 어떻게 확보하나 (헷갈리지 않도록 명시)

- 데이터레이크에는 SteamSpy의 `positive`/`negative` **집계 숫자만** 있고 리뷰 원문 텍스트는 전혀 없음
  (PRD에 적힌 Reddit 수집도 실제로는 미구현 상태) → 리뷰 원문 수집 자체가 신규 작업
- 명작 아카이브 게임: `old_games_pipeline`이 이미 appid를 갖고 있으므로 그대로 재사용, 추가 발굴 불필요
- RSS 뉴스 게임: 기사에서 추출한 게임명을 Steam 공식 `storesearch`(이름 검색) API로 매칭. 이건
  `recent_games_pipeline`이 겪었던 "날짜 필터가 서버에서 무시되어 카탈로그 전체를 순회해야 하는" 문제와는
  **다른 종류의 호출** — 게임명 1건당 API 콜 1번으로 끝나는 정상 동작하는 엔드포인트라 같은 병목이 재발하지 않음

## "게임과 무관"이라는 표현에 대한 정정

- 초기 대화에서 감성분석 섹션을 "게임과 무관한 독립 섹션"이라고 잘못 표현한 적이 있음
- 정확한 의미: 감성분석은 **명작 아카이브 섹션(항목 2)에 종속되지 않는 독립 섹션**이라는 뜻이며,
  분석 대상 자체는 당연히 게임 리뷰임. 게임 자체와 무관하다는 뜻이 아님 — 혼동 방지를 위해 기록
